# 테스트 계획

사용자 장비에서 확인한 결과와 자동화 결과를 별도로 기록한다.

## 기준선과 준비

1. 원본 SHA, macOS·iOS, 빌드 도구, 케이블 경로, 화면 모드, 오디오 출력, 브라우저 및 필터 버전을 남긴다.
2. 무수정 빌드 후 원본 Swift·웹 테스트 중 고정 버전에 해당하는 항목을 실행한다. 빌드·테스트 명령, 종료 코드, 앱 경로를 기록한다.
3. 아이폰과 Mac을 동일 신뢰 Wi-Fi/LAN에 연결한다. 맥북을 열고 두 화면을 확장 모드로 설정하며 오디오 출력을 내장 스피커로 선택한다.
4. 기존 앱·사용자 설정을 보존하고 기준선과 변경판을 같은 조건에서 비교한다. 필요한 계정은 사용자가 로그인하고 기록에서 인증 정보를 제외한다.

### 격리 실행

`v0.22`의 `MACTV_DATA_DIR`은 앱 파일과 페어링 저장 위치를 바꾼다. `UserDefaults`와 기본 WebKit 저장소도 분리하기 위해 빌드 앱을 `local-test-data/baseline-v0.22/Mac TV Baseline.app`에 복사했다. 복사본의 번들 ID는 `local.couch.tv.custom.baseline.v022`이며, 로컬 임시 서명으로 다시 서명했다. 설치 앱에는 변경을 가하지 않았다. 기존 Chromium 프로필을 사용하지 않도록 실기기 기준선에는 내장 플레이어를 사용한다.

프로젝트 루트에서 테스트 복사본을 실행한다.

```bash
test_root="$PWD/local-test-data/baseline-v0.22"
MACTV_DATA_DIR="$test_root/data" \
  "$test_root/Mac TV Baseline.app/Contents/MacOS/MacTV" \
  -automaticUpdates NO -analyticsConsent declined -keepMacAwake NO -remotePort 8775
```

격리 복사본을 다시 만들 때는 `build/Mac TV.app`을 별도 경로에 복사하고, 복사본의 `Info.plist`에서 `CFBundleIdentifier`를 위 값으로 설정한다. 프로젝트 루트에서 `codesign --force --entitlements Assets/MacTV.entitlements --sign - "$test_app"`으로 복사본을 서명한다. 여기서 `test_app`은 복사본의 절대 경로다.

첫 `./build.sh` 및 Swift 테스트는 사용자 Clang 캐시 쓰기 권한 때문에 종료 코드 1로 종료됐다. 웹 레이아웃 테스트도 루프백 수신 권한(`EPERM`)으로 종료 코드 1이 발생했다. 권한을 허용한 재시도에서 Swift·웹 테스트가 통과했다. 원본 빌드 재시도는 도중에 세션이 중단되어 산출물이 없었고, 동일 소스로 다시 빌드해 성공했다. 컴파일러는 Intel 아키텍처 사용과 일부 원본 API 사용에 대해 경고를 출력했다.

### 3단계 밝기 변경판 · 2026-11-25

- `./build.sh`, `codesign --verify --deep --strict`, `lipo -archs`로 로컬 임시 서명과 `arm64`·`x86_64` 빌드를 확인했다. Chrome 웹 테스트 8종이 통과했다. Documents 밖 소스 사본의 `swift test --skip-build --disable-xctest`에서 Swift 142개 테스트와 신뢰 기기·표시 대상·범위 검사 테스트가 통과했다.
- M1에서 내장 밝기를 `DisplayServices`로 읽고 34% → 40% 쓴 후 40%를 읽었다. 기존 34%로 복원하고 다시 읽었다. 실기기 앱은 `local-test-data/brightness-v0.22/Mac TV Brightness Test.app`이며, 별도 번들 ID와 임시 데이터 경로를 사용한다.
- LG 32UP830을 USB‑C로 직결한 상태에서 BetterDisplay 5.2.1 직접 DDC 밝기 조회는 `Failed.`(종료 코드 1), m1ddc `9d75fb6`의 기본 및 120·180ms 지연 조회는 `no valid reply`(종료 코드 1)를 반환했다. 대비와 입력 조회에도 응답하지 않았다. 현재 하드웨어 값과 최대값을 읽을 수 없어 쓰기는 미실행으로 남겼다. BetterDisplay의 일반 밝기 값은 하드웨어 DDC 값으로 사용하지 않는다.
- LG에 커서를 올리고 맥북 F2를 눌렀을 때 사용자가 LG가 밝아졌다고 확인했다. BetterDisplay의 소프트웨어 밝기는 75% → 100%, 일반 밝기는 37.5% → 50%로 읽혔고 하드웨어 필드는 0 그대로였다. 이 키 조작에서 소프트웨어 감광이 변경됐다. 같은 앱의 CLI로 소프트웨어 밝기를 75%로 복원하고 읽기값을 확인했다. [BetterDisplay 밝기 안내](https://betterdisplay.pro/guide/faq/brightness/monitor-percentage-mismatch/)
- 첫 전체 Swift 실행과 단독 재시도에서 선택 실행인 `RemoteReconnectLive`가 `Timed out waiting`으로 실패했다. 직전 유튜브 변경판에서도 같은 명령, 같은 위치에서 시간 초과가 재현됐다. 아이폰의 실제 재연결은 별도 확인이 필요하다.

#### LG 소프트웨어 밝기 적용

- 신뢰 기기로 인증된 리모컨 요청 경로를 실제 LG에 적용했다. 직접 DDC 조회 실패 후 `(Software)` 방식으로 75%를 읽었다. 80%를 설정하고 같은 방식으로 읽은 뒤 75%로 복원했다. 그동안 맥북 내장 밝기는 50%를 유지했다. 표시 방식과 다른 DDC 쓰기 요청은 HTTP 409로 거절했다.
- 서명 검증을 통과한 `arm64`·`x86_64` 로컬 빌드, Swift 142개 및 웹 테스트 8종을 확인했다. 웹에서는 LG 슬라이더를 놓을 때 소프트웨어 방식과 해당 화면 ID가 포함된 요청 한 건이 전송되고, 내장 값은 바뀌지 않는지 확인했다.
- 아이폰용 격리 앱은 별도 번들 ID 및 임시 데이터 경로를 사용한다.
- 아이폰에서 두 슬라이더 조작, 케이블 재연결·잠자기 복귀, HDR·색상 영향은 확인 대기다. LG 직접 DDC는 조회 무응답이어서 하드웨어 밝기 쓰기는 미실행이다.

#### 화면별 밝기 프리셋과 정밀 조절

- Chrome의 아이폰 크기 터치 시뮬레이션에서 0·25·50·75·100% 버튼, 짧은 트랙 탭, 약 350ms 누른 뒤 드래그, 터치 취소를 검증했다. 62% 드래그 중에는 쓰기 요청이 없었고, 손을 뗐을 때 해당 화면에 한 번 전송됐다. 취소 시 이전 값이 복구됐고 내장 화면 값은 유지됐다.
- 로컬 빌드와 서명 검증, Swift 142개 및 웹 테스트 8종이 통과했다. 사용자 실기기에서 LG 100% 버튼으로 값을 설정했으며, 당시 리모컨의 소프트웨어 밝기 100%는 BetterDisplay 팝업의 통합 밝기 50%로 표시됐다. 길게 눌러 드래그하는 동작은 아이폰에서 확인 대기다.

#### BetterDisplay 밝기 눈금 일치

- LG에서 이전 `softwareBrightness` 100%는 `brightness` 50%에 해당했다. BetterDisplay 일반 밝기를 75%로 올렸을 때 사용자가 화면이 실제로 더 밝아졌다고 확인했다. 외장 대체 경로의 읽기와 쓰기를 `brightness`로 바꾸고 리모컨에 `(BetterDisplay)`를 표시했다. 직접 DDC 읽기와 별개다.
- 실제 LG의 신뢰 리모컨 요청 경로에서 통합 밝기 50% → 100% → 50%를 확인했다. 100%를 적용하자 리모컨 응답과 BetterDisplay CLI가 모두 100%를 보고했다. 맥북 내장 밝기 50%는 유지됐고 LG를 50%로 복원했다.
- 로컬 빌드와 서명 검증, Swift 142개 및 웹 테스트 8종이 통과했다. 최신 테스트 앱은 `local-test-data/brightness-combined-v0.22/Mac TV LG Brightness Test.app`이며 기존 테스트 페어링을 사용한다.

### 4단계 측면 OSD · 2026-11-25

- `./build.sh`, `codesign --verify --deep --strict`, `lipo -archs`로 서명된 `arm64`·`x86_64` 빌드를 확인했다. 웹 8종과 Swift 144개가 통과했다. Swift 첫 실행은 고정 대기 후 패널 닫힘을 검사하는 새 테스트가 실패했다. UI 상태가 실제로 갱신될 때까지 제한된 시간 안에 확인하도록 테스트를 수정해 재실행했다.
- macOS 창에서 좌우 배치, 마우스 입력을 받지 않는 패널, 키 창 유지와 자동 닫힘을 검증했다. 전체화면은 Swift 테스트 러너에서 재생 창을 키 창으로 만들 수 없어 임시 macOS 앱으로 재검증했다. 실제 전체화면 Space에 패널 두 개가 표시됐고 재생 창이 키 창을 유지했으며 둘 다 자동으로 닫혔다.
- 아이폰용 앱은 `local-test-data/side-osd-v0.22/Mac TV OSD Test.app`이다. 밝기 대상 화면, 음량 표시 화면, 영상 조작과 외부 Chrome·IINA 전체화면은 실기기 확인 중이다.

### 5단계 아이폰 리모컨 화면 · 2026-11-25

- 신뢰 리모컨의 **Settings → Display & sound**에서 내장 스피커 음량과 화면별 밝기를 조절한다. Swift 테스트는 신뢰·게스트 접근, 잘못된 값, 변경 전 출력 ID 거절을 검증했다.
- Chrome의 아이폰 크기 뷰포트 6종에서 기존 조작과 레이아웃을 확인했다. 음량 미리보기와 1회 쓰기, 음소거, 긴 장치 이름, 외부 오디오 출력으로 바뀔 때 비활성 상태, 연결 끊김과 복구 후 현재값 표시를 확인했다.
- 실제 M1 내장 스피커를 신뢰 리모컨 요청 경로로 13% → 17%로 바꿨다. API 응답과 실제 Core Audio 읽기값이 일치했고 13%로 복원했다.
- 로컬 `arm64`·`x86_64` 빌드와 서명 검증, Swift 145개 및 웹 테스트 8종이 통과했다. 최신 아이폰용 앱은 `local-test-data/remote-controls-v0.22/Mac TV Remote Test.app`이며 기존 테스트 페어링을 사용한다. 아이폰 실기기 확인은 대기 중이다.

### 6단계 통합 빌드 · 2026-11-25

- `./build.sh --custom` 2회와 `./build.sh`를 실행했다. 종료 코드 0. `build/MacTV Custom.app`은 `local.couch.tv.custom`, 개발용 `build/Mac TV.app`은 `local.couch.tv`임을 확인했다. 커스텀 빌드는 임시 서명으로 검증됐고 `arm64`·`x86_64` 바이너리, 최신 리모컨 리소스와 라이선스가 들어 있다. 앱의 Info.plist에서 원본 TelemetryDeck 앱 ID는 제거됐다.
- 서명 검사에 종료 코드 19를 주입해 실패를 재현했다. 이전 앱 경로와 파일 식별자가 유지됐고 기존 서명도 유효했다.
- `MACTV_DATA_DIR` 없이 최종 앱을 두 번 실행하고 정상 종료했다. `~/Library/Application Support/MacTV Custom/Icons` 생성을 확인했다. 앱이 제공한 리모컨 페이지는 HTTP 200이었고 미페어링 `/state`는 HTTP 401이었다. 기존 설치 앱의 번들 ID는 `local.couch.tv`로 유지됐다.
- `swift test --disable-xctest` 145개, 웹 8종, 별도로 실행한 `RemoteReconnectLive` 1개가 통과했다. 이전에 시간 초과됐던 Bonjour 재연결은 이번 실행에서 1.35초에 통과했다.
- 최종 앱에서 새 QR 페어링, iPhone Safari의 홈·재생·밝기·음량, 기존 권한이 필요한 외부 플레이어 동작을 확인할 수 있도록 앱을 열었다. 손쉬운 사용 권한 유지, 최종 아이폰 조작·재연결, 서비스별 재생 세부 결과는 확인 대기다.

### 공개 DMG 패키징 · 0.1.0

- `bash scripts/make-custom-dmg.sh`로 압축 DMG와 SHA‑256을 생성했다. 이미지 검사와 체크섬 검증, 읽기 전용 마운트에 성공했다. 내부 앱의 서명·`arm64`와 `x86_64`·표시 버전 `0.1.0`과 `Applications` 바로가기를 확인했다.
- `release`의 SemVer 태그에서 실행되는 GitHub Actions가 테스트 후 DMG를 게시한다. 빌드 및 배포 절차는 [브랜치와 배포](RELEASING.md)에 기록했다.
- 첫 `v0.1.0` 태그를 푸시한 뒤 배포 워크플로 실행이 표시되지 않아 로컬 검증 파일을 직접 게시했다. GitHub가 표시한 DMG와 체크섬 파일의 SHA‑256이 로컬 파일과 일치했다. 태그를 바탕으로 한 자동 게시의 첫 실행은 아직 확인하지 못했다. [첫 공개 릴리스](https://github.com/Cocomong98/MacTV-Custom/releases/tag/v0.1.0)
